## java中的锁

在 `MyLinkedQueue` 的实现中，选择了 `ReentrantLock` 作为同步机制。
```java
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notEmpty = lock.newCondition();
```
下文将分析为什么选择 `ReentrantLock`，以及其他锁机制的特点和适用性。

#### 为什么使用 `ReentrantLock`？

-   **独占性保证线程安全**
    入队（`offer`）和出队（`poll`）操作都会修改链表的头尾指针及节点内容，必须保证同一时刻只有一个线程执行这些操作，因此需要一个独占锁。`ReentrantLock` 正是可重入的独占锁。

-   **需要条件变量实现等待/通知**
    出队操作在队列为空时需要等待，直到有元素入队。`ReentrantLock` 提供了 `Condition`（`notEmpty`），可以精确地使消费者线程等待，并由生产者线程在入队后唤醒，避免了使用 `synchronized` 时只能有一个等待集且容易产生虚假唤醒的问题。

-   **支持可中断的锁获取**
    `poll` 方法使用了 `lockInterruptibly()`，允许线程在等待锁的过程中响应中断。这在实现超时等待时尤为重要，如果使用 `synchronized`，线程在尝试进入同步块时无法被中断（除非已持有锁）。

-   **支持超时等待**
    `poll` 方法接收超时参数，通过 `notEmpty.awaitNanos(nanos)` 实现限时等待。`Condition` 的 `awaitNanos` 可以精确处理剩余等待时间，并返回剩余 `nanos`，方便循环控制。

-   **性能与灵活性**
    `ReentrantLock` 在竞争激烈时表现良好，且可以配置公平性（默认为非公平），提供了比 `synchronized` 更多的控制能力。

#### 其他可用的锁及其特点

1.  **`synchronized` 关键字**
```java
    public static class MyLinkedQueue<E> {   
        private final Object lock = new Object();
        // 入队操作
        public boolean offer(E e) {
            synchronized (lock) {
                Node<E> node = new Node<>(e);
                tail.next = node;
                tail = node;
                // 增加计数并唤醒等待的消费者
                count.incrementAndGet();
                lock.notify();
            }
            return true;
        }

        // 出队操作
        public E poll(long timeout, TimeUnit unit) throws InterruptedException {
            long nanos = unit.toNanos(timeout);
            long deadline = System.nanoTime() + nanos;
            synchronized (lock) {
                while (count.get() == 0) {
                    if (nanos <= 0)
                        return null;
                    // wait接受的是毫秒
                    long timeoutMs = TimeUnit.NANOSECONDS.toMillis(nanos);
                    if (timeoutMs <= 0 && nanos > 0) {
                        // 如果有纳秒但不足1毫秒，等待1毫秒，避免快速自旋
                        timeoutMs = 1; 
                    }
                    lock.wait(timeoutMs);
                    nanos = deadline - System.nanoTime();
                }
                
                Node<E> first = head.next;
                E x = first.item;
                first.item = null;
                head = first;
                
                count.decrementAndGet();
                return x;
            }
        }
    }
```

-   **特点：**
    -   隐式锁，使用简单，无需手动加锁解锁。
    -   自动释放锁（异常或正常退出同步块）。
    -   每个对象只有一个等待集（通过 `wait()`/`notify()`/`notifyAll()`），无法像 `Condition` 那样区分多个条件。
    -   锁获取过程不可中断（线程阻塞在 `synchronized` 入口时无法响应 `interrupt()`）。
    -   不支持超时获取锁，但可通过 `wait(long timeout)` 在持有锁后实现超时等待。
    -   可能锁膨胀：在高竞争情况下，JVM 可能将轻量级锁升级为重量级锁，在低并发时追求性能（轻量级），在高并发时保证公平（重量级）。
-   **是否适用于本例？**
    理论上可以用 `synchronized` 替代，但 `poll` 方法中的 `lockInterruptibly()` 难以直接实现。需先获取锁，然后循环检查队列状态，调用 `wait(timeout)` 等待。但若线程在等待锁时被中断，无法响应；且 `wait` 的超时精度不如 `awaitNanos`。因此 `synchronized` 不能满足本例的全部需求。
-   性能报告：
```text
平均总耗时: 1.44 ms/req
----------------各步骤平均耗时----------------     
Step1(GetCourse): 0.00 ms
Step2(Bloom)    : 0.00 ms
Step3(FullCheck): 0.18 ms
Step4(Conflict) : 0.04 ms
Step5(Type)     : 0.01 ms
WaitValid       : 0.21 ms
Step6(Save)     : 0.98 ms
平均总耗时: 1.44 ms/req，其中 `Step6(Save)` 和 `WaitValid`总共占了约 1.19 ms，即其他开销为 0.25 ms。相比 `ReentrantLock` 的 0.21 ms，性能有所下降。
```

2.  **`ReentrantReadWriteLock`**
```java
public static class MyLinkedQueue<E> {
        private final ReentrantReadWriteLock lock = new ReentrantReadWriteLock();
        private final Condition notEmpty = lock.writeLock().newCondition();
        // 入队操作
        public boolean offer(E e) {
            lock.writeLock().lock();
            try {
                Node<E> node = new Node<>(e);
                tail.next = node;
                tail = node;
                // 增加计数并唤醒等待的消费者
                count.incrementAndGet();
                notEmpty.signal();
            } finally {
                lock.writeLock().unlock();
            }
            return true;
        }

        // 出队操作
        public E poll(long timeout, TimeUnit unit) throws InterruptedException {
            long nanos = unit.toNanos(timeout);
            lock.writeLock().lockInterruptibly();
            try {
                while (count.get() == 0) {
                    if (nanos <= 0)
                        return null;
                    nanos = notEmpty.awaitNanos(nanos);
                }
                
                Node<E> first = head.next;
                E x = first.item;
                first.item = null;
                head = first;
                
                count.decrementAndGet();
                return x;
            } finally {
                lock.writeLock().unlock();
            }
        }
    }
```
-   **特点：**
    -   分离读锁（共享）和写锁（独占），适用于读多写少的场景。
    -   读锁可被多个线程同时持有，写锁独占。
    -   也支持 `Condition`，但写锁可以关联条件，读锁不能。
-   **是否适用于本例？**
    不适合。因为入队和出队都会修改队列结构（写操作），必须独占锁。使用读写锁反而会增加复杂度，且可能引入不必要的性能开销。
-  性能报告：
```

----------------各步骤平均耗时----------------     
Step1(GetCourse): 0.00 ms
Step2(Bloom)    : 0.00 ms
Step3(FullCheck): 0.19 ms
Step4(Conflict) : 0.04 ms
Step5(Type)     : 0.01 ms
WaitValid       : 0.22 ms
Step6(Save)     : 1.10 ms
平均总耗时: 1.58 ms/req，其中 `Step6(Save)` 和 `WaitValid`总共占了约 1.32 ms，即其他开销为 0.26 ms。相比 `ReentrantLock` 的 0.21 ms，性能明显下降。
```

3.  **`StampedLock`**
    -   **特点：**
        -   JDK 8 引入，支持三种模式：写锁、悲观读锁和乐观读。
        -   乐观读允许在读操作时不加锁，之后通过版本戳验证数据是否被修改。
        -   不可重入，且不支持 `Condition`。
    -   **是否适用于本例？**
        不适合。队列的入队/出队都是写操作，需要独占锁；且需要条件等待，`StampedLock` 无法提供 `Condition`，在此不再测试。

4.  **基于 `AbstractQueuedSynchronizer`（AQS）自定义锁**
    -   **特点：**
        -   可自行实现符合特定需求的同步器，灵活度高。
        -   需要深入理解 AQS 原理，代码复杂且易出错。
    -   **是否适用于本例？**
        理论上可行，但没必要。`ReentrantLock` 已经提供了完备的功能，自定义锁会引入不必要的维护成本。在此不再测试。

5.  **使用无锁算法（如 `AtomicReference` 实现链表）**
    -   **特点：**
        -   基于 CAS 操作实现非阻塞队列，例如 `ConcurrentLinkedQueue`。
        -   性能更高，但实现复杂，且无法直接支持阻塞等待（需要结合 `LockSupport` 等）。
    -   **是否适用于本例？**
        不适用。本例的 `poll` 方法要求当队列为空时阻塞等待，这需要锁和条件变量配合。无锁队列通常无法直接提供阻塞语义。在此不再测试。

#### 锁机制特点对比

| 特性 | ReentrantLock | synchronized | ReentrantReadWriteLock | StampedLock |
| :--- | :--- | :--- | :--- | :--- |
| **独占性** | 独占 | 独占 | 写锁独占，读锁共享 | 写锁独占，读锁共享/乐观读 |
| **可重入** | 是 | 是 | 是 | 否 |
| **条件变量** | 支持（多个） | 仅一个（wait/notify） | 写锁支持，读锁不支持 | 不支持 |
| **可中断锁获取** | 支持（lockInterruptibly） | 不支持（等待锁时不可中断） | 支持 | 支持 |
| **超时锁获取** | 支持（tryLock） | 不支持 | 支持 | 支持 |
| **公平性选择** | 支持 | 非公平 | 支持 | 非公平 |
| **性能（低竞争）** | 较好 | 较好 | 略低（维护读锁状态） | 乐观读性能高 |
| **性能（高竞争）** | 较好 | 可能下降（锁膨胀） | 可能下降（读锁竞争） | 可能下降（写锁竞争） |

#### 结论
`ReentrantLock` 是当前实现的最佳选择，它提供了所需的全部特性：独占锁、条件变量、可中断锁获取和超时等待。其他锁要么缺少关键功能，要么不适合该场景。在并发编程中，应根据具体需求选择合适的锁机制，既要满足功能性要求，也要考虑性能和复杂度。

## 锁的分类

### 1. 按宏观态度：悲观锁与乐观锁

#### 悲观锁
悲观锁总是假设最坏的情况，认为每次访问共享资源时都可能发生冲突，因此每次操作都会加锁，阻塞其他线程的访问。这种策略适用于写操作频繁、冲突概率高的场景。

- **实现方式**：通过操作系统或 JVM 的锁机制实现，线程被阻塞后会让出 CPU，进入阻塞状态。
- **Java 代表**：`synchronized` 关键字、`ReentrantLock` 等显式锁。
- **优点**：简单直接，能严格保证数据一致性。
- **缺点**：阻塞和唤醒线程会带来上下文切换开销，高并发下可能降低吞吐量。

#### 乐观锁
乐观锁假设冲突很少发生，每次访问不加锁，而是在更新时检查期间数据是否被修改过（通过版本号或 CAS 操作）。如果被修改，则重试整个操作。适用于读多写少、冲突概率低的场景。

- **实现方式**：通常基于硬件支持的 CAS（Compare-And-Swap）指令，或版本号机制。
- **Java 代表**：`java.util.concurrent.atomic` 包下的原子类（如 `AtomicInteger`、`AtomicReference`），`StampedLock` 的乐观读模式。
- **优点**：无阻塞，无上下文切换，吞吐量高。
- **缺点**：在冲突频繁时会导致大量重试，可能浪费 CPU 资源；且只能保证单个共享变量的原子性，对复杂操作需配合其他手段。

### 2. 按获取锁的公平性：公平锁与非公平锁

#### 公平锁
公平锁严格按照线程请求锁的顺序分配锁，先到先得，不会产生饥饿现象。

- **实现方式**：通常需要维护一个等待队列，每次唤醒队列头部的线程。
- **Java 代表**：`ReentrantLock` 构造器传入 `true` 可创建公平锁。
- **优点**：公平，避免线程饥饿。
- **缺点**：上下文切换更频繁，吞吐量通常低于非公平锁。

#### 非公平锁
非公平锁允许线程插队，即新到达的线程可以尝试抢占锁，若成功则直接获取，若失败才进入等待队列。这可能导致某些线程迟迟得不到锁（饥饿），但能减少线程挂起和唤醒的开销。

- **实现方式**：线程获取锁时先直接尝试 CAS 抢占，失败再排队。
- **Java 代表**：`synchronized`（非公平）、`ReentrantLock` 默认非公平。
- **优点**：吞吐量较高。
- **缺点**：可能造成饥饿，且需要处理重试机制。

### 3. 按可重入性：可重入锁与非可重入锁

#### 可重入锁
可重入锁允许同一个线程多次获取同一把锁，而不会产生死锁。锁内部维护一个持有计数，每次获取加一，每次释放减一，直到计数为零才真正释放锁。

- **Java 代表**：`ReentrantLock`、`synchronized`。
- **优点**：避免线程在递归调用或嵌套同步时死锁，简化编程模型。

#### 非可重入锁
非可重入锁不允许线程重复获取自身已持有的锁，否则会死锁（如自旋锁实现不当）。某些锁为了特定性能优化或功能限制而设计为非可重入。

- **Java 代表**：`StampedLock` 的写锁是不可重入的，如果线程再次尝试获取已持有的写锁会阻塞或抛出异常。
- **适用场景**：需要严格控制锁的持有层次，或实现简单自旋锁时。

### 4. 按锁的共享方式：共享锁与独占锁

#### 独占锁（排它锁）
独占锁保证同一时刻最多只有一个线程持有锁，其他线程必须等待。适用于写操作，防止数据被并发修改。

- **Java 代表**：`ReentrantLock`、`synchronized`、`ReentrantReadWriteLock` 的写锁。
- **特点**：严格保证数据一致性，但并发度低。

#### 共享锁
共享锁允许多个线程同时持有锁，通常用于读操作，因为读操作不修改数据，可以并发进行。共享锁常与独占锁配合实现读写分离。

- **Java 代表**：`ReentrantReadWriteLock` 的读锁、`StampedLock` 的悲观读锁。
- **特点**：提高读多写少场景的并发性能。

### 5. 按阻塞/自旋方式：自旋锁与适应性自旋锁

#### 自旋锁
自旋锁是指线程在尝试获取锁失败时，不会立即阻塞，而是循环检查锁状态（自旋），直到锁被释放。自旋避免了线程切换的开销，但如果锁被持有时间较长，会浪费 CPU 资源。

- **实现方式**：通常基于 CAS 和循环。
- **Java 代表**：`java.util.concurrent.atomic.AtomicReference` 可构造简单自旋锁；`ConcurrentLinkedQueue` 等无锁数据结构也隐含自旋思想。
- **适用场景**：锁持有时间极短，且竞争不激烈的场景。

#### 适应性自旋锁
适应性自旋锁是 JVM 对自旋锁的优化，它会根据上一次在同一锁上的自旋时间和锁的持有状态，动态调整自旋次数（甚至不再自旋）。这避免了固定的自旋次数带来的资源浪费。

- **Java 代表**：`synchronized` 在轻量级锁阶段会采用适应性自旋。
- **优点**：自适应策略能在保证性能的同时避免过度自旋。

### 6. 其他分类维度

#### 偏向锁、轻量级锁、重量级锁
这是 `synchronized` 在 JVM 中的锁升级过程（锁膨胀）的不同阶段，体现了锁针对不同竞争程度的优化。

- **偏向锁**：锁会偏向于第一个获得它的线程，后续该线程进入同步块无需任何同步操作，适用于只有一个线程访问同步块的场景。
- **轻量级锁**：当有其他线程竞争时，偏向锁撤销，升级为轻量级锁。轻量级锁通过 CAS 尝试获取锁，若失败则自旋，适用于线程交替执行同步块的场景。
- **重量级锁**：若轻量级锁自旋失败，或竞争激烈，则膨胀为重量级锁，线程被阻塞，由操作系统管理。

#### 分段锁
分段锁不是一种具体的锁，而是一种锁的设计思想，将数据分段，每段独立加锁，从而提高并发度。典型代表是 `ConcurrentHashMap` 在 Java 7 中的实现（Segment 继承 ReentrantLock）。

#### 显式锁与隐式锁
- **隐式锁**：由 JVM 自动管理加锁释放，如 `synchronized`，使用简单但功能受限。
- **显式锁**：需要程序员手动加锁释放，如 `ReentrantLock`，提供更多灵活性和控制能力（如中断、超时、多个条件等）。

### 小结

锁的分类维度众多，且各种分类相互交织。例如 `ReentrantLock` 既是悲观锁，又是可重入锁、独占锁，支持公平/非公平选择，还提供了条件变量。在实际开发中，选择合适的锁需要综合考虑：

- **操作类型**：读多写少考虑读写锁，写多读少考虑独占锁。
- **竞争程度**：低竞争可用乐观锁或无锁，高竞争需悲观锁。
- **功能需求**：是否需要中断、超时、多个等待条件等。
- **性能要求**：吞吐量、延迟、公平性之间的权衡。

## 事务

### 1. 事务的定义与 ACID 特性

**事务**（Transaction）是数据库管理系统执行过程中的一个逻辑工作单元，由一组数据库操作组成，这些操作要么全部成功执行并持久化，要么全部不执行（即回滚到事务开始前的状态）。事务是保证数据一致性和完整性的基础机制。

事务必须满足四个关键特性，即 **ACID**：

- **原子性（Atomicity）**：事务中的所有操作被视为一个不可分割的整体，要么全部成功，要么全部失败回滚。例如在抢课场景中，插入选课记录的操作必须完整执行，不能出现只插入了部分数据的情况。
- **一致性（Consistency）**：事务执行前后，数据库必须保持一致性状态。例如选课后，课程剩余名额减少、学生选课记录增加，这两个状态变化必须同时反映，不能出现名额已减但记录未生成的不一致现象。
- **隔离性（Isolation）**：多个事务并发执行时，彼此的操作应互不干扰，避免出现脏读、不可重复读、幻读等问题。数据库通过锁或多版本并发控制（MVCC）来实现隔离。
- **持久性（Durability）**：事务一旦提交，其对数据库的修改就应永久保存，即使系统崩溃也不会丢失。

在抢课等高并发场景中，事务确保了选课操作的可靠性：当多个学生同时抢同一门课时，事务能保证每个学生的选课请求独立、完整地执行，避免因并发导致的数据错乱。

### 2. 使用 `@Transactional` 管理事务

注册并使用 `studentCourseSelectionService.saveSelectionWithTransaction(newSelection);` 来操作数据库。
具体使用的是 `@Transactional` 注解来管理事务，代码如下：
```java
    @Transactional(rollbackFor = Exception.class)
    public void saveSelectionWithTransaction(StudentCourseSelection studentCourseSelection) {
        boolean saveSuccess = this.save(studentCourseSelection);
        if (!saveSuccess) {
            throw new RuntimeException("Save course selection failed");
        }
    }
```

-   `@Transactional` 是 Spring 提供的一个核心注解，用于声明方法需要在一个事务上下文中执行。它可以应用在接口、类或方法上，通常建议在具体类或方法上使用，因为 Spring 的代理机制有时无法正确处理接口上的注解。
-   当标注了 `@Transactional` 的方法被调用时，Spring 会通过 AOP 拦截该方法，在方法执行前开启事务，方法执行后根据是否有异常来决定提交或回滚事务。（默认情况下只有外部调用才会触发事务增强。如果类内部方法直接调用（如 `this.method()`），则事务不会生效。解决方法包括使用代理对象调用或调整设计。）
-   事务的开启、提交、回滚等操作由底层的事务管理器（如 `DataSourceTransactionManager`、`JpaTransactionManager` 等）负责。
-   `@Transactional` 提供了多个可配置属性，用于精细控制事务行为：
    -   `propagation`：事务的传播行为（如 `REQUIRED`、`REQUIRES_NEW` 等）。
    -   `isolation`：事务的隔离级别（如 `READ_COMMITTED`、`REPEATABLE_READ` 等）。
    -   `timeout`：事务的超时时间（秒）。
    -   `readOnly`：是否为只读事务，用于优化（如 Hibernate 可能会跳过 flush 操作）。
    -   `rollbackFor` / `rollbackForClassName`：指定哪些异常触发事务回滚。
    -   `noRollbackFor` / `noRollbackForClassName`：指定哪些异常不触发事务回滚。

这里的 `rollbackFor = Exception.class` 用于定义触发事务回滚的异常类型。其行为是：
-   将回滚条件扩展到所有 `Exception` 及其子类（包括运行时异常和检查型异常）。
-   这意味着当方法抛出任何 `Exception` 类型的异常时，事务都会被标记为回滚，最终不会提交。

### 3. 性能分析

在高并发抢课场景下，使用 `@Transactional` 注解会引入一些性能开销，主要体现在以下几个方面：
从 0.7ms 增加到 1.2ms (增加了约 0.5ms)，原因如下：

1.  **数据库连接交互：**
    -   **非事务模式：** 可能在某些配置下利用了隐式的自动提交，或者连接池复用更轻量。
    -   **事务模式 (`@Transactional`)：** Spring 需要显式地从连接池获取连接 -> 关闭自动提交 (`set autocommit=0`) -> 执行 SQL -> 提交事务 (`commit`) -> 归还连接。这中间涉及到至少两次额外的数据库网络交互（关闭自动提交和提交事务）。

2.  **数据库侧开销：**
    数据库需要开启一个新的事务上下文，分配事务 ID，记录 Undo Log（用于回滚）和 Redo Log（用于持久化），这些都需要额外的磁盘 I/O 或内存操作。

#### 结论
在高并发抢课场景下，数据一致性高于这 0.5ms 的性能损耗。如果不加事务，万一发生极其罕见的数据库异常，可能会导致数据状态不一致。
不过，`saveSelectionWithTransaction` 方法内部只包含这一条 `save` 语句，其实 MyBatis Plus 的 `save` 方法本身就是单条 SQL 原子操作，数据库层面默认就是作为一个隐式事务执行的，所以在这种特定场景下，其实可以考虑不使用 `@Transactional` 注解，直接调用 `save` 方法，这样就能避免上述的额外开销。
